# v0.3 멀티플레이와 메뉴

이 파일은 이전 버전의 검토 기록입니다. 현재 계정 진입·무작위 스타팅·리플레이 삭제 안내는 [v0.4 문서](multiplayer-v04.md)를 사용하세요.

멀티플레이 진입 시 주소 입력 없이 로비에 연결하고 방 목록을 엽니다. 기본 지휘관 계정은 PC에 생성·저장하며, 계정 버튼으로 다른 PC의 계정에 로그인할 수 있습니다. 계정·점수는 연결한 로비 서버에 저장됩니다.

## 연결 범위

공용 로비 주소가 배포되지 않은 기본 구성은 **같은 네트워크에서의 플레이**입니다. 클라이언트가 UDP 17801로 로비를 탐색하고, 탐색된 서비스가 없으면 번들된 `runtime/node.exe`로 로컬 로비를 자동 실행합니다. 로비 HTTP 포트는 TCP 17800, 전투는 UDP 17900~18000입니다. 자동 검색이 공유기·방화벽에 의해 차단되는 환경에서는 다른 PC의 로비를 찾지 못할 수 있습니다.

인터넷 전체 사용자가 공유하는 방 목록은 항상 접속 가능한 공용 로비가 필요합니다. 운영자가 실행 파일 옆 `network.json`에 `{"lobby_url":"https://운영중인-로비-주소"}`를 배포하면 자동 탐색 대신 해당 서비스에 연결합니다. 이 버전에는 실제 운영 중인 공용 서비스 주소가 포함되지 않았습니다. 소스에는 빈 주소의 `network.example.json`만 있습니다.

공용 로비를 운영할 때는 `PUBLIC_HOST`를 외부에서 접근 가능한 전투 서버 호스트로 지정하고 UDP 전투 포트도 열어야 합니다. HTTP 연결만으로 전투 UDP 경로가 제공되지는 않습니다.

## 준비와 시작

방장도 직접 준비해야 합니다. 두 명 이상의 참가자가 모두 준비하면 서버가 5초 카운트다운을 시작합니다. 남은 시간이 3초보다 많으면 준비 취소로 카운트다운을 중단할 수 있습니다. 남은 3초부터는 준비 취소, 종족·팀·맵 변경이 서버에서 거부됩니다.

나가기·연결 끊김은 잠금 중에도 시작을 취소합니다. 전투 생성 직전에 모든 사람의 최근 폴링을 확인하며 응답이 끊긴 참가자가 있으면 시작하지 않습니다. 참가자 구성 변경도 진행 중인 카운트다운을 취소합니다. 카운트다운을 마친 커스텀 전투는 모든 클라이언트가 접속하면 별도 3초 대기 없이 시작합니다.

래더는 기존 1000점 시작, K=40 Elo, 서버 결과 판정과 점수 반영 방식을 유지합니다. 커스텀 전투는 래더 점수를 바꾸지 않습니다.

## 메뉴

싱글플레이, 설정, 방 목록, 대기실, 래더, 리플레이는 기존 메인 배경 위의 생성형 보드 팝업으로 열립니다. 팝업 전환 시 이전 보드는 제거하고 같은 배경을 유지합니다. 게임 메뉴와 환경 설정은 게임 화면과 HUD 위에 열리며, 로컬 전투는 일시 정지하고 온라인 전투는 계속 진행됩니다.

실제 로컬 전투 시작 또는 온라인 참가 슬롯이 확인된 첫 전투 스냅샷에서 `settings.last_played_race`를 저장합니다. 다음 실행의 메인 배경, 설정 보드 및 버튼 색상은 이 종족을 사용합니다. 플레이 기록이 없으면 바위너구리(0)를 사용합니다. 메뉴에서 다음 종족을 선택하는 것만으로는 최근 플레이 종족을 바꾸지 않습니다. 보드 이미지는 `assets/modal_board_r{race}_v3.png`를 우선 사용합니다.

## 검증

- `tests/lobby_countdown_test.js`: 자동 5초 시작, 3초 잠금, 준비 취소, 나가기·끊김 보호, 티켓과 점수 보존을 인프로세스 API로 검증합니다.
- `tests/server_test.js`: 계정·매칭·결과·히스토리·Elo 회귀 검사입니다.
- `tests/menu_modal_v03_test.gd`: 같은 배경/HUD 보존, 보드 교체, 주소 필드 제거, 준비 버튼 잠금을 검증합니다.
- `tests/network_test.js`: 소켓 사용이 가능한 환경에서 실제 ENet 참가자와 매치를 검사합니다. 인프로세스 검사만으로 인터넷 연결 성공을 보장하지 않습니다.

검증 환경에서 실제 네트워크 검사는 `/health` 접근 전에 차단되었습니다. `tests/loopback_diagnostic.js`로 독립 확인한 결과, 서버의 `127.0.0.1` listen은 정상이고 proxy 환경변수도 없었지만 Node fetch와 node:http 모두 `127.0.0.1` 및 `localhost` 연결에서 `EACCES`를 받았습니다. Godot HTTPRequest도 두 주소 모두 응답을 받지 못했고 서버 수신 요청은 0회였습니다. 이는 테스트 환경의 로컬 소켓 접근 제한이며, 실제 두 클라이언트의 ENet 전투 성공을 검증한 결과가 아닙니다. 소켓 접근이 가능한 PC에서 `tests/network_test.js`를 다시 실행해야 합니다.
