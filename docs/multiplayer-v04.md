# v0.4 멀티플레이·메뉴·리플레이

멀티플레이는 서버 주소 입력 없이 로비를 찾은 뒤 **직접 정한 닉네임으로 가입하거나 로그인**해야 방 목록과 래더에 들어갑니다. 닉네임은 2~16자, 비밀번호는 6~100자입니다. 신규 계정은 1000점으로 시작하며, 계정·점수는 연결한 로비 서버에 저장됩니다. 클라이언트는 다음 로그인에 쓸 닉네임만 기억하고 새 비밀번호 파일을 만들지 않습니다.

## 연결 범위와 버전

기본 구성은 같은 네트워크에서의 플레이입니다. UDP 17801 검색에 응답하는 protocol 4 로비가 없으면 번들된 `runtime/node.exe`로 로컬 로비를 실행합니다. 로비는 TCP 17800, 전투는 UDP 17900~18000을 사용합니다. 이전 버전 서비스에는 계정·시작 위치 형식이 달라 연결하지 않습니다. 자동 검색이 공유기나 방화벽으로 차단되면 다른 PC의 로비를 찾지 못할 수 있습니다.

인터넷 전체 사용자가 공유할 방 목록에는 운영 중인 공용 로비가 필요합니다. 배포자가 실행 파일 옆 `network.json`에 `{"lobby_url":"https://운영중인-로비-주소"}`를 설정하면 해당 서비스로 연결합니다. 기본 배포에는 운영 중인 공용 주소가 없습니다. 공용 운영자는 `PUBLIC_HOST`와 UDP 전투 포트를 외부에서 접근할 수 있게 제공해야 합니다.

## 이전 자동 계정

v0.3의 자동 생성 규칙은 40자리 소문자 hex 비밀번호와 `지휘관`+그 앞 12자리 닉네임이었습니다. 기존 `commander.json`이 이 규칙과 정확히 일치하면 클라이언트는 `/account/legacy`에 기존 자격 증명을 제출합니다. 서버는 실제 저장된 비밀번호 해시까지 확인한 계정만 `legacy_generated`로 표시해 순위에서 제외하고 신규 멀티 접속을 거부합니다. 계정·점수·승패·경기 기록은 삭제하지 않습니다.

이름이 비슷하다는 이유만으로 계정을 제외하지 않습니다. 다른 PC의 기존 자동 계정도 해당 PC가 자격 증명을 제시할 때 검증됩니다. 증명되지 않은 과거 계정을 임의로 분류하거나 삭제하지 않습니다.

## 전장·스타팅·준비

래더 전장은 전투 생성 시 서버가 세 맵 중 균등 추첨합니다. 클라이언트가 제출한 맵이나 시작 위치는 래더 선택에 사용하지 않습니다. 커스텀은 방장이 선택한 맵을 유지합니다.

서버는 커스텀과 래더 모두 네 스타팅을 Fisher–Yates로 섞어 플레이어 수만큼 고유한 `spawn_slots`를 전투 설정에 저장합니다. `players` 배열·소유자 ID·팀·결과 슬롯은 바꾸지 않습니다. 전투 코어는 서버 확정 배열을 그대로 사용하며, 클라이언트의 HTTP 응답에는 자기 시작 위치만 전달합니다.

방장도 직접 준비해야 합니다. 두 명 이상이 모두 준비하면 서버가 5초 카운트다운을 시작합니다. 남은 3초부터 준비 취소와 종족·팀·맵 변경을 거부합니다. 나가기, 참가자 변경, 최근 응답이 끊긴 참가자는 카운트다운을 취소하므로 보이지 않는 참가자와 자동 시작하지 않습니다. 커스텀은 준비 카운트다운을 마친 뒤 별도 3초 대기를 반복하지 않습니다.

래더는 K=40 Elo를 유지합니다. 동점 상대와는 약 ±20, 200점 높은 상대에게 이기면 약 +30, 200점 낮은 상대에게 이기면 약 +10입니다. 점수는 서버가 확인한 결과에서 한 번만 반영하며 커스텀은 바꾸지 않습니다.

## 화면

커스텀 대기실은 왼쪽에 실제 전장의 128×128 지형·자원·네 스타팅 미니맵과 맵/방식 설정, 오른쪽에 네 참가자 슬롯·종족·팀·준비 상태를 표시합니다. 미니맵은 전투와 같은 `ACMap` 데이터에서 그립니다. 순위표는 서버 기록을 순위·닉네임·점수·승·패·승률의 실제 컬럼으로 표시합니다.

싱글·설정·멀티·리플레이는 같은 메인 배경 위의 종족 생성형 보드를 사용합니다. 마지막 실제 플레이 종족을 저장해 다음 실행의 메인·설정·버튼 색상에 적용합니다. 싱글 팝업의 전투 조작 설명은 제거했습니다. 승리/패배는 전장과 HUD 위에 같은 종족 보드를 열고 전투 기록, 서버 래더 결과, 메인 화면과 리플레이 버튼을 보여 줍니다.

## 리플레이 삭제

각 리플레이 행에 재생·삭제 버튼이 있습니다. 삭제는 선택한 파일명이 보이는 종족 팝업에서 확인하며 취소하면 파일을 유지합니다. `.acr` 단일 파일명만 허용하고, 정규화된 절대 경로가 `user://replays`의 직접 자식인지 검증합니다. 절대 경로, 경로 탈출, 폴더, 심볼릭 링크·정션은 거부합니다. 삭제 뒤 목록과 빈 상태를 갱신하고, 현재 재생하던 파일을 지웠다면 그 재생 상태만 정리합니다.

## 검증과 남은 범위

- `tests/server_v04_test.js`: 명시 계정, 증명된 자동 계정 제외와 기록 보존, 실제 승률, 전장·스타팅 서버 권위, 입력 검증을 격리된 인프로세스 서비스에서 검사합니다.
- `tests/server_test.js`, `tests/lobby_countdown_test.js`: 계정·Elo·결과·준비 카운트다운 회귀 검사입니다.
- `tests/menu_v04_test.gd`: 실제 메인 씬을 상속하되 HTTP는 fixture로 대체해 새 화면·계정 진입·결과·삭제 범위를 검사합니다. `tools_run_menu_v04.js`는 엔진 오류가 나면 즉시 실패합니다.
- `tests/font_v04_test.gd`: 동일 서체로 변환한 Galmuri TTF의 한글과 실제 문자열 폭을 Godot로 검사합니다.

검증 환경에서는 Node fetch·node:http의 `127.0.0.1`/`localhost` 연결이 `EACCES`로 차단되었고 Godot HTTPRequest도 응답을 받지 못했습니다. 서버 listen은 정상이었지만 수신 요청이 0회였습니다. 따라서 인프로세스·화면 검사는 실제 두 클라이언트의 ENet 전투나 공용 인터넷 접속 성공을 의미하지 않습니다. 소켓 접근이 가능한 환경에서 `tests/network_test.js`를 실행해야 합니다.
